`retrieve`/`delete` silently issue a different query than the one typed when a value contains a reserved character: `retrieve systems hostname=a&ipaddress=1.2.3.4` sends an extra `ipaddress` filter, and a value with a space or `#` becomes a second bogus parameter. Values rendered from server data via `foreach` hit the same path, so response text corrupts the next request with no warning — which can feed a destructive `foreach`.

`src/mash/app.py:572-580` (at `36b6a5e`): each whole token including its value is appended verbatim to `queryString` (`:580`); nothing URL-encodes it — a hand-built query string instead of passing a mapping to requests.

**Fix:** Parse tokens into a key-value mapping and pass it as the `params` argument of `session.get`/`session.delete` (or urlencode each value with `urllib.parse`), rejecting tokens that are not `key=value` before building the request. Independent of #36's validation gap.

Impact: touches query-string building on GET/DELETE; prod today reserved characters in a value silently change the query sent, expected: values URL-encoded as request params. Files: `src/mash/app.py`.

Severity: S3 — silent request corruption under ordinary-but-special inputs.
