## 2. Per-candidate assessment

### 2.1 Card title / summary generation — nothing to route
Session titling is already an aux call on qwen36-fast (`auxiliary.title_generation`, live traffic confirmed). **Kanban** card titles and completion summaries, by contrast, are authored by the worker model as arguments inside its ordinary `kanban_create`/`kanban_complete` tool call — there is no separate LLM call to relocate. Inserting one would add a call, a failure mode, and an inconsistency between title and body, to save zero tokens (the text is a few dozen tokens the worker had in context anyway). Hermes does offer `prefer_fast_model` on the title slot — a provider fast-tier hint that is moot here since the slot is already pinned to the fastest alias. **Verdict: already solved / no benefit.** (Confidence: high — verified in ledger + config_defaults source.)

### 2.2 Butler intake pre-triage / routing classification — fast model already in the seat
Butlers run `qwen38-flash-fp8` — which is itself the estate's fast tier (TTFT p50 0.9 s). The routing decision (meta-work vs board work, which board) is made with the routing-doctrine doc in-context, is supervised (the butler lists-then-creates, G-02/G-08 apply), and is cheap to correct when wrong. A ≤2B pre-classifier in front of a 0.9 s-TTFT fast model saves nothing a human perceives, and a misroute pushes a wrongly-filed card into the orchestrator — cost asymmetric to the ~zero savings. `triage_specifier` / `kanban_decomposer` aux slots already exist for exactly this shape and are pinned to glm53 by deliberate choice (routing children to specialist profiles is the expensive-to-get-wrong part; ~4 calls/day is not a cost problem). **Verdict: no benefit; keep glm53 on decompose unless volume or trivially-templated triage volume changes the math.** (Confidence: high.)

### 2.3 Distiller-gate pre-filter — wrong tool, wrong volume
The distiller gate is the estate's public-filing gate (G-06: `VERDICT: PASS|REJECT` + sha256 + operator `clarify` GO before any public submission). It runs per-filing, a few times a day at most, on glm53 (a judgment seat by census). The "obviously malformed submission" check is deterministic (missing VERDICT line, sha mismatch, empty body) — that is regex/code, and code pre-checks cost zero. A model pre-filter before a supervised model gate saves nothing at this volume and risks false-rejecting a valid filing, which burns operator time. **Verdict: no; if a guard is wanted, it's code, not a model.** (Confidence: high.)

### 2.4 Dispatcher-adjacent classification — deterministic code already does it
The dispatcher is code, not a model: claim locks/expiry, PID liveness, heartbeats, `dispatch_stale_timeout_seconds: 14400`, `failure_limit: 3`, concurrency caps. Stuck-task detection is arithmetic on timestamps — a model would be strictly worse (nondeterministic, slower, unexplainable). Duplicate pre-screen: the recorded duplicate incidents were **orchestration races** (two writers, one hour, G-08 origin story), which no similarity model fixes; `idempotency_key` + single-intake-channel target the actual cause, and the sibling embedding report shows FTS5 brute-force at 1.3k cards is sub-millisecond. **Verdict: no benefit — this is code's job.** The one code-side idea worth relaying (not model work): ER2-C's optional dispatcher backpressure signal (defer low-priority batch cards when the alias queue depth in orb `/metrics` is high) — that targets the real p99 problem from the dispatcher side. (Confidence: high for the verdict; the backpressure note is ER2-C's.)

### 2.5 `goal_judge` — the one clean, free win
Kanban cards can run in `goal_mode` (worker loops until an auxiliary judge agrees the work is done). That judge is a native aux slot — `goal_judge` in `config_defaults.py`, described as "satisfaction + contract drafting; JSON calls" — and it is **absent from every fleet config**, so it runs on the worker's main model, which for goal-mode cards on the judgment tier means glm53 at p99 362 s per judge call. This is a binary, low-stakes, high-frequency-per-card classification — the textbook fast-model task (by shape, what the RND-4/5 program called "system-1" work), with a native pin already provided. Judge error cost is low (an early stop is visible on the card; a wasted extra turn costs minutes). Goal-mode usage in this estate is currently rare (0 rows in window), so the win is small in absolute terms — but the pin is zero-risk and one line. **Recommendation: `auxiliary.goal_judge: {provider: litellm, model: qwen36-fast, reasoning_effort: none}` fleet-wide, at the architect's next config pass.** (Confidence: high on mechanism — source-verified; volume claim is window-limited.)

### 2.6 `background_review` — the biggest genuine unexploited lever, but measure first
Hermes runs a post-turn self-improvement fork (save memory / patch skills) on **every session** by default (`background_review.enabled: True`), and the default routes it to **the main model replaying the full conversation** (warm cache). The upstream comment is explicit: an explicit model instead "replay[s] a compact digest (~3–5x cheaper)". Across 60 profiles × continuous kanban traffic this is the one place where the estate is systematically paying judgment-model prices for a summarization-and-curation task. Caveats that keep this a "measure then pilot" instead of "adopt now": (a) the fork does not appear in the aux-ledger (0 rows) — it likely rides the main call path, so its true volume/cost must be measured from per-profile session DBs or orb SpendLogs by an owner with shell/SQL; (b) routing it off-main also changes memory-curation quality (a digest instead of full replay), which the operator may value; (c) it inherits reasoning config to keep the parent's prompt-cache warm, so savings are model-dependent. **Recommendation: one measurement pass (ER2-C's `er2c_sess.py` pattern over session DBs, background_review token share by profile), then pilot `background_review` → `qwen38-flash-fp8` on 1–2 glm53 lanes and compare curation output quality for a week.** (Confidence: mechanism high — source-verified; economics medium — volume unmeasured, this is the honest gap.)

## 3. Why gargantua02's STAYS-BIG does not transfer (and what it does say)

- **Different risk class.** CAP-2A demands ≥99 % agreement + zero false-safe on a frozen production approval corpus; every ≤12B candidate failed (best 82.5 %, MiniCPM5-2B). Hermes' internal decision points are reversible and supervised (retryable cards, review columns, operator clarify gates), so the bar is "cheap and mostly-right with visible failure," not "99 % agreement." On that bar the estate's existing qwen36-fast aux layer clears it in practice (0.67 % hard-failure rate; compression mis-summarization degrades a session, not a production serve).
- **The one genuine overlap is instructive, not alarming:** Hermes' `approvals.mode: smart` already delegates command-risk *triage* to qwen36-fast (`auxiliary.approval`, 125 calls/4.5 d) — i.e., the estate accepted, upstream-by-default, exactly the pattern gargantua02 refused: a small model in the approval path. It's tolerable here because the failure mode is "operator gets prompted / doesn't get prompted for a command inside an agent session on their own machines," backed by the deny-ruleset (e.g. the litellm config path) and G-32's declared exception — a categorically smaller blast radius than an unattended serving gate. No action; recorded because the operator asked how the two programs relate.
- **What transfers:** the CAP lesson that small models fail on **estate-blast-radius reasoning** (they read a command locally-safe) is precisely why the estate keeps decompose/routing/distiller/architect judgment on glm53. The estate's division — qwen36-fast for shape-tolerant micro-decisions, glm53 for judgment, code for arithmetic — is the right reading of the tournament evidence, and it is already the as-built state.

## 5. Recommendation

1. **No new small fast model, no dedicated instance, no RND-4/5 reuse. No serving/hosting card is warranted.**
2. **Adopt (zero-risk, next fleet config pass, kanban-board-architect's lane):** pin `auxiliary.goal_judge` → `qwen36-fast` (reasoning off). One line, native slot, a textbook fast-model task currently paying main-model prices.
3. **Measure, then pilot:** quantify `background_review` token volume per profile from session DBs/SpendLogs; if material (plausibly the largest hidden aux cost on the 28 glm53 lanes), pilot routing it to `qwen38-flash-fp8` on 1–2 lanes for a week with a curation-quality check before fleet-wide.
4. **Protect the existing fast-aux lane instead of expanding it** — ER2-C C-4 (`auxiliary.compression.fallback_model: glm53` on the 23 qwen38-flash lanes), C-5 (Hindsight LLM concurrency 16→8), C-3 (proxy metadata window drift). These raise the reliability of the aux lane the estate already depends on; each is one line / one env var, all operator/architect-gated.
5. **Housekeeping (harmless-but-misleading config cruft):** `auxiliary.web_extract` and `auxiliary.session_search` blocks in fleet configs are ignored upstream now; the `providers.litellm.models.qwen38` pin is dead (ER2-C notes). Drop at the next drift pass.

**Revisit triggers (so this doesn't get re-researched):**
- Goal-mode becomes a standard card pattern (judge volume × main-model price makes the pin urgent — though #2 already pre-empts it).
- Any new webhook/chat intake at >~1k msgs/day needing <500 ms pre-classification (that is the one workload shape where a MiniCPM5-class GPU serve enters the conversation; today no such intake exists — butler intake is ~300 operator msgs/day across 5 butlers, comfortably inside the existing fast lane).
- Skill catalog > ~300 entries/profile, or card volume > ~10k (same triggers the embedding card registered).
- If gh201 becomes materially more loaded (Hindsight consolidation bursts already push Hermes qwen36-fast p99 to 22 s vs Hindsight's own 7 s), the discussion shifts from "add a small model" to "second aux deployment" — ER2-C §5 option B (4 Gaudi shadow lane with qwen36-fast as benchmark candidate) already owns that decision.
