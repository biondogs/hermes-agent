## 2. Hermes side (ga01)

- **Root profile** `~/.hermes/config.yaml` already pinned `timezone: America/New_York` (top-level
  key) — no change needed; `hermes config get timezone` → `America/New_York`.
- **All 60 profile config.yaml** now pin `timezone: America/New_York` (58 were unpinned; set via
  `HERMES_HOME=<profile> hermes config set timezone America/New_York`; 2 already had it:
  sampling-test, unsloth-litellm). Unpinned profiles previously fell back to **server-local = UTC**
  (ga01 was Etc/UTC); after the host TZ change they resolve to ET either way — the pin makes it
  explicit and host-TZ-independent.
- **Cron semantics** (verified in source `hermes_time.py` + `cron/jobs.py`): schedules evaluate in
  the profile-configured zone; unpinned → server-local. Stored `next_run_at` instants are absolute
  and do not move on a zone change.
- **Before/after cron tables** (root namespace): every enabled root job's `next_run` is
  byte-identical before and after (e.g. `nightly-skill-evolution 0 3 * * *` → 2026-10-24T03:00-04:00
  both passes; `nightly-board-audit 0 4 * * *` → 04:00-04:00). **Jobs already intended in ET kept
  identical fire times.**
- **UTC-assuming expressions documented:**
  - `kanban-board-architect` → `weekly-estate-maintenance` (`0 4 * * 0`): stored next_run was
    UTC-anchored (2026-10-25T04:00:00+00:00 = Sun 00:00 ET). After the ET pin, it fires once at the
    stored instant, then re-anchors to **Sunday 04:00 ET** weekly — the "4 AM Sunday" the name
    implies. This is the only cron-expression job whose absolute fire time shifts (+4 h, once),
    and it shifts *toward* the intended ET semantics per the ruling.
  - `gaudi-watcher` → `1843-replyloop-monitor-v3` (`every 30m`) and `g02-watcher` →
    `g02-azure-watch-vigil` (`every 20m`): interval schedules — absolute cadence preserved,
    zone-independent. Observed live: g02-watcher rescheduled to `14:53:31-04:00` (ET display)
    with unchanged 20-min cadence immediately after the change — **proof the live scheduler
    evaluates in ET already**.
  - System `/etc/crontab` on ga01 contains only stock Debian maintenance entries
    (cron.daily 6:25, e2scrub 03:00/03:30 Sun, sysstat 10-min); no custom UTC-assuming system jobs.
- **Gateway bounce: NOT required.** The multiplex gateway's process-local timezone cache

## 3. ga01 anomaly worth an operator look (follow-up card filed)

`/etc` on ga01 is **owned by arch:arch** (755), and `/etc/localtime` (symlink) and `/etc/timezone`
were arch-owned too (since corrected to root:root? **No — left as found**, see below). Consequences:
- `systemd-timedated` runs with `CapabilityBoundingSet=CAP_SYS_TIME` + `NoNewPrivileges=yes`
  (no DAC override) and **cannot write into arch-owned `/etc`** → `timedatectl set-timezone` fails
  "Access denied/Permission denied" on this host while working on hosts with root-owned /etc.
- The TZ change was made the DAC-legal way (arch owns `/etc`): `/etc/localtime` →
  `/usr/share/zoneinfo/America/New_York`. Verified: `readlink`, `date`, fresh `timedatectl` all ET.
- **`/etc/timezone` still reads `Etc/UTC`** (cosmetic; glibc + timedatectl + systemd all use
  `/etc/localtime`). Correcting it needs a single interactive-approved write
  (`printf 'America/New_York\n' > /etc/timezone`) — blocked in unattended mode by the local
  approval policy; deferred to follow-up card rather than probing for bypasses.
- Recommendation for the operator: decide whether `/etc` should be re-owned to root:root
  (it is the root cause of the timedated failures and a general oddity). Not changed unattended.
