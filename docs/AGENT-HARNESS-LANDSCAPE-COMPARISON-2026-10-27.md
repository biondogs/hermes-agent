## 1. Our pattern, as built (the comparison baseline)

From the as-built docs, live-stamped: 1 host (ga01), one multiplex gateway, **60 profiles**, **7 boards** (one SQLite DB each), **5 butlers**, **22 Hindsight banks**, one global dispatcher (15 s tick, 24/8 concurrency, failure_limit 3, auto-decompose, 4 h stale reclaim).

Load-bearing characteristics, in the vocabulary we will score alternatives against:

| # | Characteristic | As-built carrier |
|---|---|---|
| P1 | **Task graph with dependency gating as the durable state** | Board cards: `parents=[...]` at create, auto-promote on parent done, statuses `triage→todo→ready→running→review/blocked/scheduled→done/archived`; board DB is the audit ledger |
| P2 | **Persistent role-specialized identities** | Profiles = `config.yaml` (model, toolsets, approvals) + `SOUL.md` (role + standing laws) + own `.env` credentials + skills + memory bank; survive across runs, restarts, and projects |
| P3 | **Worker = fresh process per card, profile-pinned, env-fenced to its board** | Dispatcher spawn with `HERMES_KANBAN_DB/BOARD` pins; per-profile `kanban.board` pin + tool-layer fence (hotfix `602ea0a874`) |
| P4 | **Gated external action** | Distiller gate (PASS/REJECT + sha256), review column, operator-GO ceremony for public filings, `approvals.deny`, cron_mode deny, External Comms Law |
| P5 | **Separated memory namespaces** | 22 Hindsight banks on env-axis (one hardware estate = one bank) + role banks; butler banks never mix |
| P6 | **Long-running/async work decoupled from agent sessions** | hjob (systemd-run transient units, restart-safe), watchers, wake drivers, heartbeats, scheduled cards, 4 h stale reclaim + re-claim |
| P7 | **Butler-first intake topology** | One non-executing chat front-end per board; workers never intake; fail-safe on `default` |
| P8 | **Least-privilege toolsets per role** | Butler terminalless; research read-only; orchestrator kanban-only; deny-lists per profile |
| P9 | **Governance as data** | GOVERNANCE.md law registry, incident-earned design ledger, nightly audits, DR backups, graveyard conventions |
| P10 | **Human-in-the-loop as routing, not blocking** | `kanban_block(kind=needs_input)` parks a card and notifies; the system keeps flowing around it |

The estate is best described as **a persistent staffed organization with a durable ticket system and written law**, not "a multi-agent framework." Most of the alternatives below are frameworks for *one ephemeral piece of work*. That framing difference drives nearly every score in the table.

## 3. Per-tool assessment against **our actual needs**

Scored against how we actually work: multi-estate infra ops + SDLC + upstream filing, cross-day horizons, operator-gated externals, private models via LiteLLM, one operator.

**LangGraph** (docs: checkpointers, persistence/durable-execution). The strongest *execution substrate* in the field: per-super-step checkpoints in threads, explicit durability modes, interrupt-based HITL, cross-thread stores. Honest assessment of where it is **more aligned** than us: mid-run recoverability. Our workers checkpoint at *task* granularity (bank receipts, heartbeats, re-claim); if a worker dies at 90 % of a long card we restart the card, not the exact step. LangGraph would resume the exact super-step. But its graph is *authored in code by a developer before the work exists*; ours is *filed as data while the work is happening* by butlers and decomposers. Adopting LangGraph would mean re-encoding every intake as a graph deploy — a type change from "company" to "workflow app", losing P2/P4/P5/P7/P9 wholesale. Verdict: **not a migration target; one borrowable idea** (durable step checkpointing — see §5).

**CrewAI** (docs: hierarchical-process, memory concepts). Roles are prompt attributes (`role/goal/backstory`) inside one kickoff; hierarchical process adds an LLM manager that delegates and validates — the shape of our orchestrator lane, but ephemeral, prompt-only, with no enforcement (community reports even show manager+tools combos breaking). Memory is nice for a run (scoped `/agent/researcher` banks, recency/semantic/importance scoring) but has no env-axis isolation law behind it — the exact contamination class we were burned by on 2026-10-23 (g02 workers recalling gaudi HPU lore) would be the default failure mode. No durable queue, no artifact gates, no operator ceremony. Verdict: **less aligned than us in every dimension we care about; nothing to adopt** beyond confirming scoped-memory is table stakes (we have it).

**AutoGen / AG2** (docs: group-chat intro, GroupChatManager, ConversableAgent). Conversation-centric orchestration with flexible speaker selection and handoffs. Its state is a chat transcript, its lifecycle is a chat, its HITL is `human_input_mode` on a live loop (the human must be *there*). Our doctrine is the inverse: humans are notified asynchronously and the board flows around blocked cards. Group chat for *coordination style* is a pattern we already use inside one process (delegation/subagents) without adopting the framework. Verdict: **not aligned.**

**MetaGPT** (arXiv 2308.00352v7 + source walkthrough). The most *architecturally similar* framework to us and worth being explicit about why: typed artifact handoffs, roles that activate only when prerequisite artifacts exist (dependency gating!), pub/sub message pool, executable feedback. It validates two of our core patterns: cards-with-acceptance-criteria as the artifact contract, and evidence-gated promotion. But it is an **assembly line that runs once** — a project is one Team run from requirement to QA report, then archived. We are a standing company: the same `sw-reviewer` seat reviews week 1 and week 20, with memory. Its ablation data (each role monotonically reduces human revisions; single-Engineer produces runnable code 0 % of the time on SoftwareDev) is direct external evidence *for* our staffed-lanes design. Verdict: **confirms our architecture; not a migration candidate; no borrowing needed** (our review/distiller lanes already exceed its QA-gate concept).

**OpenHands** (docs: sandboxes overview, enterprise conversations-and-sandboxes). Where it is genuinely **ahead of us: sandbox isolation.** Every execution happens in a Docker/remote sandbox; the host the operator trusts is not the host the agent trashes. We execute workers directly on ga01 protected only by approvals/deny + SOUL law + fences — our F24-class findings (CLI bypasses the tool-layer fence) are exactly the incident class containers make structurally impossible. It also models conversation lifecycle cleanly (`WAITING_FOR_CONFIRMATION`, sandbox STARTING→RUNNING→PAUSED, reconcile-after-restart guidance — the same problem as our F26/F27 bounce findings). But its unit of work is one coding conversation; there is no persistent staff, no board DAG, no multi-estate routing, no memory taxonomy. Verdict: **not a replacement; one strong borrowable property: sandboxed execution for dev lanes** (§5).

**SWE-agent / mini-swe-agent** (README; architecture page). Deliberately *not* orchestration — "the 100 line AI agent", bash-only, no tool-calling interface, >74 % SWE-bench verified. We already use it correctly (benchmark harness under `kanban-worker-full`). The relevant reading of it for this report is the opposite-of-us thesis it embodies: a huge single loop with a smart model beats scaffolding *for benchmark-sized tasks*. Our estate exists precisely for the work where that thesis stops holding: multi-day, cross-estate, externally-gated, stateful operations. Verdict: **complement, not competitor. Keep.**

**Devin / Cognition** (docs intro; June-'24 product update; third-party guide). Commercial analog of two of our ideas: **Machine Snapshots** (persisted dev environments so a session "hits the ground running") and **Knowledge** (org tribal rules across sessions). Sessions are sized to ~3-hour human tasks and parallelized — which is our card sizing philosophy from the commercial side. It is closed, cloud, single-tenant-platform, with no self-hosted model path (we are all-LiteLLM-private), and its gates are platform toggles, not an auditable law registry. Verdict: **not viable for this estate; one concept worth tracking** (environment snapshots for our fleet lanes — we approximate with worktrees + devops cards).

**Claude Code — subagents / agent view / agent teams / dynamic workflows / Projects** (docs: agents overview, workflows, sub-agents, SDK subagents). Our nearest first-party-competitor and already piloted here (claude-code pilot docs 2026-10-24). Their own docs table concedes the key distinction: with subagents/teams, intermediate results live "in Claude's context window" or a session-scoped task list; workflows are "resumable **in the same session**"; only Projects (cloud) run across days — and on Anthropic's terms. Where it is **ahead: per-task context isolation done trivially** (spawn subagent → own window → summary returns) and **workflow scripts that hold the loop in code** — our answer to both is card discipline + child cards (R6c), which costs more tokens by design. Where we are ahead: cross-session persistence (their wall is our baseline), role memory, gates, multi-board isolation, model freedom. Agent teams (shared task list + inter-agent messaging, experimental, disabled by default) is the *feature shape* of our kanban, but experimental, session-bound, and single-machine. Verdict: **use as a tool inside the estate (already the plan); not an orchestration replacement.**

**AutoGPT** (classic README + CLAUDE.md walkthrough, platform overview). Classic is officially unsupported ("experimental project… concluded its initial research phase") with a single propose→execute loop whose own docs call continuous mode dangerous and note unbounded state.json growth — the historical cautionary tale our whole design ledger is implicitly written against. The Platform is a visual block/workflow automation product (FastAPI + Postgres + marketplace), aimed at no-code automations, not staffed long-horizon engineering. Verdict: **historical reference only.**

**Kanban-native multi-agent projects** (the card asked specifically):
- **saltbo/agent-kanban** (493★, active, FSL→Apache2): *the closest project on the planet to our topology* — an agent-first task board where agents are first-class members with cryptographic identity (ed25519), roles, loadable skills, self-organizing into teams, on top of multi-runtime execution including **ACP-compliant agents, with Hermes explicitly named as supported**. Its tagline is its philosophy: **"Take human out of the loop"** — the exact inverse of our operator-final-GATE doctrine. It is a general-purpose board other runtimes dial into, not an operating system for a private multi-estate fleet: no memory banks, no distiller/comms law, no per-project board isolation with fences, no butler intake. Verdict: **strongest external validation that our architecture choice is where the ecosystem is converging; watch it, maybe interoperate via ACP someday; not a migration target.**
- **quentintou/agent-board** (31★, ~6 commits, dormant): Kanban + DAG deps + review gates + auto-retry + JSONL audit + MCP server, for OpenClaw agent teams. Independently reinvents (at toy scale) our P1 + review-column + audit-trail. Confirms convergence again; no substance to adopt.
- **Kanabanana** (BSL): self-hosted 7-column board with a dependency-aware orchestrator that spawns Claude/Gemini/LM-Studio agents per task — a *dev-board flavored* version of our dispatcher; human-facing, single-project, no governance stack.
- **vibe-kanban / dweigend/kanban-orchestrator**: human-front-end boards for orchestrating parallel coding-agent runs (switch agents, parallel/sequential, review, dev servers). Good UX references for the ops surface; wrong scope (single developer's coding agents ≠ estate operations).

Also read this run: **arXiv 2603.26458** ("Can AI Models Direct Each Other?") — uses org-structure probes to show models trained as *monolithic agents* underperform as managers/directors inside hierarchies. External research support for why our lanes are *role-scoped executors with written contracts* rather than agents freely directing each other, and why routing is done by doctrine/cards (and a human-butler) rather than emergent delegation.

## 4. Honest findings

**Is there a project more aligned with what we are doing?** **No.** No external tool combines: persistent credentialed role identities with least-privilege toolsets · durable dependency-gated task graphs per project with audit · artifact+human gate chains before external action · environment-isolated memory · async long-horizon operation with reclaim/watch/wake patterns · all self-hosted on private models. The kanban-native projects converge on our *surface* (board-as-hub) but none carries our *governance depth*; the frameworks carry *execution mechanics* we don't primarily need and lack the *organization model* we primarily do need.

**Where alternatives are genuinely ahead of us** (do not manufacture, do not hide — these are real):
1. **Execution isolation** (OpenHands): we run untrusted-on-behalf code on the host itself; containers/VMs would make several of our incident classes (fence bypass F24, approval-evasion) structurally impossible instead of law-enforced.
2. **Mid-run durable state** (LangGraph): task-granular checkpointing means a dead worker = a re-run, not a resume. We paper this with bank-receipt discipline (R6c) — which is discipline, not mechanism.
3. **Zero-friction context isolation** (Claude Code subagents/workflows): per-task windows and code-held loops cost us real tokens; their per-turn isolation is nearly free for the sizes of task they target.
4. **Environment reproducibility** (Devin machine snapshots; partly OpenHands images): lanes re-derive dev environments via worktrees/devops cards; snapshot-based resumes would cut setup tokens and drift.
5. **Agent identity/attribution** (agent-kanban ed25519): our attribution is truthful-receipt *law*; they make it cryptographic. Cheap idea to steal in software (signed commit trailers mapped to profiles, verifiable by tooling).

**Where we are ahead or distinctive** (evidence-backed, not vibes): persistent profile identities with their own credentials/banks/toolsets exist in no framework above as anything beyond prompt attributes; the incident-earned governance corpus (design-intent ledger, law registry, graveyard/DR conventions, dedup/collision doctrine) is a moat no OSS project even has a vocabulary for; butler-first intake with a non-executing chat front-end per board is unique among everything surveyed; env-axis memory isolation was learned from a real contamination incident — shared-pool products will reproduce that bug class by default; and every framework's HITL is *synchronous waiting* while ours is asynchronous card-routing that keeps the fleet moving.

## 5. Recommendation: **STAY, plus five borrowable patterns (as recommendations only — no config was touched on this card)**

Migration is not warranted; a migration would spend months re-implementing P1/P2/P4/P5/P7 as third-party features while discarding the incident-earned corpus that makes them safe. Adopt selectively:

1. **Sandbox dev lanes (from OpenHands' model)** — pilot Docker-sandboxed workspaces for `sw-dev-a/b` and `kanban-worker` execution while keeping law-gated host access for ops lanes. Highest-value single change; addresses finding (a) in §4. *Route: architect card → kanban-board-architect lane for any fleet change.*
2. **Checkpoint-per-step discipline → mechanism (from LangGraph's durability modes)** — we already bank receipts at task granularity; formalize "checkpointed phase" as a card metadata convention so re-claimed cards resume at phase boundaries. Cheap, doctrinal, no new runtime.
3. **Signed agent attribution (from agent-kanban)** — per-profile commit trailers with a verifiable signature scheme, replacing law-only truthful receipts.
4. **Lane environment snapshots (from Devin Machine Snapshots)** — golden container/dev-env images per fleet lane family, refreshed by nightly devops cards, so bench/dev lanes start from state not scripts.
5. **ACP interop watch (toward agent-kanban et al.)** — Hermes is already named as an ACP-capable runtime by at least one external board project; if the operator ever wants external agents on a board (or ours on theirs), ACP is the seam to keep an eye on. No action now.

**One anti-recommendation, explicitly:** do not adopt "take the human out of the loop" (agent-kanban's tagline) even where it's fashionable. Every law in our design ledger that the ecosystem lacks was earned by an incident this operator paid for; the operator final gate on public filings is load-bearing, not friction.
