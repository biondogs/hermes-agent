Editing a NIC, network, OS repo, or system while a jobserver is already RUNNING that regeneration job flips the running row back to PENDING: the job runs twice with different configuration data or its completion status is lost, leaving stale node configuration.

Six sites call `Job.objects.update_or_create(name=..., module=..., defaults={'status': 1})` — `networks/models.py:133-136`, `systems/models.py:372-375` and `:414`, the OSRepo signals, and the register flow at `systems/views.py:157` — all skipping the `queue_job` helper in `common/__init__.py`, which only creates when no PENDING row exists.

**Fix:** route all six sites through `queue_job`, or add a current-status guard so RUNNING or COMPLETED rows are never blindly reset.

Impact: touches change-signal job queueing for NICs, networks, OS repos and systems; prod today an edit while a job is RUNNING resets it to PENDING so it runs twice, expected: running rows never blind-reset; overlaps the claim work in mprov-ng/mprov_jobserver#112 and #296, worth doing together.
