## 2. The five most important things per repo (plain language)

### mprov_control_center — the web front door is wide open
1. **One key rules everything.** Any valid API key can read and write every
   model endpoint (CC-001, #4), and the API hands back BMC and root
   passwords in cleartext (CC-002, #5). One leaked key = fleet takeover.
2. **Power commands can hit the wrong nodes.** `hostname=` is a substring
   match silently capped at 10 systems: powering off `compute001` can power
   off `compute0010`…`compute0019` (CC-040, #43). Exact-match lookup fix.
3. **Factory defaults are admin:admin / changemenow**, baked in by the
   installer with no force-change (CC-004, #7); plus unauthenticated
   endpoints let an attacker on the provisioning net enroll its own MAC
   (CC-005, #8) or spoof X-Forwarded-For (CC-006, #9).
4. **The image NFS share is root-writable from any client** (no_root_squash,
   CC-008, #11) — a compromised node can poison every future provisioning.
5. **Production installs skip the jobqueue fixtures** (CC-020, #23): the
   job pipeline is silently broken from day one on fresh installs.

### mprov_jobserver — highest-stakes repo, five real S1s
1. **A real mPCC API key is committed in the repo** (stack.env, JS-001, #1).
   Rotate the key AND purge history — the file has carried the key since
   2024-12. This is the single most actionable item in the whole program.
2. **Secrets leak during provisioning**: distro root password in process
   argv and daemon logs (JS-002, #2); fleet API key + node root password
   written world-readable in /tmp entity.json (JS-003, #3). Any local user
   on a build host or live node can read them.
3. **It executes an unverified binary fetched into world-writable /tmp**
   (busybox, JS-004, #4) — pre-plant-and-win execution as root.
4. **Sweep-deletes are unguarded**: a mis-set image/repo directory (or an
   empty API reply) makes sync jobs rmtree arbitrary subtrees (JS-005, #5).
   Also repack_image destroys the image it repacks (JS-015, #15).
5. **The orchestrator lies about success**: script failures are swallowed
   and jobs report success (JS-010, #10); a crashed worker strands jobs in
   RUNNING forever (JS-022, #22). You cannot trust job status today.

### mprov_scripts — root-on-node scripts, zero S1 but four ordinary breakages
1. **The Ansible integration never runs** — an over-escaped jq program is a
   compile error, loop body dead (SCR-001, #1, exec-verified).
2. **Missing config keys silently write the literal string `null` into root
   password / ssh-key config** — fleet nodes become unreachable
   (SCR-002, #2; the guards exist and are bypassed).
3. **Both storage builders crash** on ordinary inputs: disk formatter on
   non-RAID partitions (SCR-003, #3), RAID build on disk-id comparison
   (SCR-004, #4).
4. **No guard against repartitioning the running OS disk** (SCR-017, #17)
   and BMC/root passwords passed in argv / world-readable temp files
   (SCR-009 #9, SCR-014 #14) — fine single-user, S1-shaped the day scripts
   re-run on multi-user nodes.
5. **12 shipped scripts are absent from the manifest** (SCR-015, #15) — they
   silently never load into mPCC; plus hardcoded python3.8 paths break
   Rocky 9 silently (SCR-016, #16).

### mash — stale but sound; plumbing is the risk
1. **The release pipeline is dead**: workflow uses retired actions + removed
   set-output syntax (MASH-023, #23). mash cannot ship a new version until
   this is fixed.
2. **Password login never authenticates** — argument indexing bug
   (MASH-001, #1); API-key connect works, user/password silently does not.
3. **BMC power verbs are unreliable**: break without a trailing slash on
   mprovURL (MASH-003, #3) and then report no success/failure at all
   (MASH-004, #4) — the operator gets no feedback on a power operation.
4. **Scripting misuse silently succeeds**: script-mode always exits 0
   (MASH-011, #11), missing files ignored (MASH-012, #12), errors pollute
   stdout (MASH-010, #10), stale MPROV_RESULT after failures (MASH-005, #5)
   — automation built on mash gets wrong answers with a straight face.
5. **Good news, stated for the record**: no breaking API drift against
   2026 CC (verified against current views), TLS verify on by default, key
   never in argv. The 2023 client still speaks the 2026 API.
